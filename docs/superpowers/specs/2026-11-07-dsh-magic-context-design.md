# DSH Magic Context 移植设计草案

## 目的与状态

解决工具输出使编程 Agent 上下文快速膨胀的问题：较旧内容能退出本轮请求，需要时仍能找到当时的原文。用户已选择固定上游版本、复用选定源码与测试、独立维护 DSH 适配层。

这是一个项目级设计草案，不是实施计划。用户尚未批准本文，也未确定完整 V1 范围；本次不创建插件骨架、不安装依赖、不修改现有 DSH 配置。初稿编写时尚无Git仓库；用户随后单独授权初始化和推送，此授权不包含插件实现。

2026-11-07：用户已批准阶段0的隔离Windows/DSH、文本/JSON、离线验证范围，并仅授权编写计划；未授权实现。阶段0计划见[验证计划](../plans/2026-11-07-stage0-context-lifecycle.md)。这不代表整个设计、完整V1或正式禁用行为已批准。

需求：[PRD 草案](https://github.com/elvisw/dsh-plugin-magic-context/blob/main/_bmad-output/initiative-dsh-magic-context/prd-dsh-magic-context/prd-dsh-magic-context.md)。事实：[固定版本研究](https://github.com/elvisw/dsh-plugin-magic-context/blob/main/_bmad-output/initiative-dsh-magic-context/research-context-lifecycle/research-context-lifecycle.md)。本文的实现选择均为提议，不能将源码研究的结论误读为运行验证成功。

## Goals

- 工具内容可逆卸载，稳定引用不因消息位置、缩减或重启而指向其他内容。
- 保留上游排队、保护、缓存感知提交与确定性重放的语义。
- 将 DSH 差异集中在边界，保留升级上游的可追踪性。
- 为 Historian、长期记忆与 UI 留出增量交付路径，不用首个技术闭环替换全部原始需求。

## Non-goals 与反目标

- 不从零重写一套相似缩减算法，不用摘要冒充精确恢复。
- 不绕过 DSH 的请求冻结契约，在 LLM 中间件偷偷改正文。
- 不承诺永久缓存命中、原始历史被删除后的恢复、任意附件的无损还原。
- 不因复用上游而直接接入、迁移或写坏用户现有 OpenCode/Pi 数据库。
- 不以“大幅减少 token 发送量”为唯一成功指标；还要观察恢复正确性、缓存成本和前台等待。

## Constraints 与版本

- MC 来源固定 `v0.49.40` / `33fb6ac9a39c8bb299776b6b514ea0815a15a225`。
- DSH 源码基线 `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`；本机 CLI 报 `0.2.2-rc.1`。版本字符串不证明发布包与源码逐文件一致。
- DSH 的请求来自持久事件派生且被冻结；上游 Transcript 是可变的当前请求表示。
- 上游没有在所检两包中公开独立通用 core SDK。源码复用需要显式构建边界与依赖清单。
- 保留 MIT 版权与许可；引入的具体依赖逐一核对许可。
- Windows 重启、真实提供商缓存、多模态与未知 DSH 版本仍需实证，不从已有测试标题推导保证。

## Approaches

1. **上游仓库新增 DSH adapter**：共享与回馈最直接，但依赖上游接纳和共同发布。
2. **固定版本源码复用＋独立 DSH adapter**：用户已选择。版本可控，既保留成熟语义也允许先解决宿主差异；代价是跟踪本地补丁与上游升级。
3. **仅参考功能重新实现**：维护自由，但容易遗漏缓存、恢复和配对约束，不符合用户选择。

用户选择的是路线2，不代表已经批准下面的模块布局、数据策略或版本切分。

## 建议的边界与数据流

```text
DSH 持久 Session 日志 ──→ 原始历史读取适配 ──→ ctx_expand 新工具结果
          │
          └──→ 当前 surface / 事件身份
                        │
      上游编号、待处理队列、保护和调度策略
                        │
                 受控变更计划
                        │
            DSH 持久 surface 变更适配
                        │
                  flush / 重启重放
                        │
                DSH 派生与冻结请求
```

[ASSUMPTION: 建议以 DSH 持久 surface 变更作为首选接入方向，不改造或替换其整个 LLM loop。] 这不是已经证明可行的最终架构。事件替换与可重放消息投影的取舍，需要先验证解释器生命周期、source 引用、工具配对、旧摘要及冷恢复约束。若契约不满足，停止并报告，不退回隐蔽正文改写。

## 复用/适配清单

| 资产 | 建议处理 | 不能直接承诺的部分 |
|---|---|---|
| 稳定身份与范围解析 | 复用逻辑，映射 DSH 会话/事件/调用身份 | 不把 surface 下标当 tag |
| 待处理队列、保护与调度 | 尽量复用策略及验证数据 | 首次应用需要与 DSH durable commit 对齐 |
| 已决定缩减模式的重放 | 保留语义，改写宿主提交边界 | 上游可变 Transcript 不能直接作为 DSH 正式请求 |
| 原始历史读取 | 复用 provider 契约和渲染，新增 DSH reader | 不读缩减后的 surface 充当原始来源 |
| 工具描述与 Agent 指引 | 复用语义，调整注册与引用说明 | 不保留宿主不支持的承诺 |
| Historian 提示、格式与校验 | 保留资产，后续接入 DSH 模型/取消/后台生命周期 | 不直接复制隐藏 OpenCode session 调用 |
| 衰减与预算 | 优先独立复用；在允许重建时改变已冻结内容 | 不每轮重排前缀 |
| SQLite、worker 与嵌入 | 按实际选用模块盘点与裁剪 | 不拖入整套宿主入口及无关 UI/daemon |
| 缓存、恢复、SIGKILL 与配对测试 | 迁移断言契约并新增 DSH fixture | 测试存在不等于本机已通过 |
| 桌面功能组织 | 参考交互与数据需求，逐步做 DSH UI | 不直接搬 Tauri 应用 |

源码来源、上游路径、提交、本地差异及对应测试应有一份可更新清单。[ASSUMPTION: 建议以后将 vendor 原始资产与 DSH 适配分开，尽量避免在 vendor 中散布宿主判断。] 具体目录由实现计划确定。

## 数据所有权与恢复契约

[ASSUMPTION: 建议以 DSH 正式持久化日志作为原始历史权威，缩减库只维护引用、决定和必要索引，不默认复制全会话。] 若 DSH 生命周期会清除恢复所需记录，必须先提出独立归档方案，不能默默失去可恢复性。

“原文”先明确为宿主已经接受并保存的文本、工具参数与结果；不能恢复采集前就被截断的 stdout，也不能从失效临时路径凭空恢复附件。是否首阶段只支持文本/JSON工具结果，需要用户确认。

缩减前必须能够持久定位原始归属。缩减元数据与 DSH 事件若属于不同存储，不假设存在跨库事务；需要持久 intent、稳定操作身份、幂等提交及恢复对账，具体协议留给技术验证和实现计划。失败时不得发出无持久依据的新缩减结果。

恢复作为新的工具返回，不撤销原缩减决定；大结果应有明确限额/分页与未返回范围提示。缺失、越界或身份不一致必须明确失败，不能混用 tag 与消息序号。

暂不改写上游存储格式，不等于已经选择全局共享数据库。按项目隔离、目录位置和文本编辑分别讨论；现有 Magic Context 数据互通也需独立迁移/兼容设计。

## 缓存与故障边界

保留上游“待处理不等于已执行、决定只产生一次、之后重放”的基本语义。模型/工具声明变化、实际缓存过期及上下文压力可能需要受控重建；不能承诺永远只追加。

DSH 的事件落地时机、模型/提供商路线和摘要插入布局都会影响前缀。任何恢复策略都应区分“原始历史可读”和“最后健康请求可重放”，不能因前者存在就跳过后者的身份/预算校验。

上游部分崩溃测试跳过 Windows，不直接沿用为 Windows 交付证明。真实缓存测试需要用户同意的提供商凭据与成本；本阶段没有调用它。

## 建议的增量边界

- **阶段0：兼容性验证候选。** 只验证稳定引用、排队缩减、DSH持久变更、重启重放、原始文本恢复与结构合法性。需批准设计后另写计划并申请进入实现；当前没有实施。
- **阶段1：上下文管理增量候选。** Historian、分层分区、确定性衰减、自动缩减/代理标记模式及缓存感知布局。
- **阶段2：捕获与回忆增量候选。** 项目记忆、统一检索、普通笔记、后台搜索提示和可选 Git 索引；具体功能可因依赖调整先后。
- **后续候选：** 插件 UI 逐步建设；复杂 Dreamer 巩固和开放条件 Smart notes 可考虑 V2。

阶段0完成不等于原始需求全部完成。普通笔记与依赖 Dreamer 的条件笔记分别排期；跨 harness 的未来可扩展与直接共享现有数据分别验收。

## 验证策略与停止条件

静态研究只证明存在接口与断言，以下为未来执行时需要验证的结果：

1. 旧工具正文离开当前请求，原始参数和结果仍可按稳定身份读取；新执行结果不能冒充原结果。
2. tag 与消息序号、重复 call ID、多工具兄弟结果不会混淆；非法/缺失引用明确报错。
3. 同一已持久化决定在重复请求、正常重启和选定失败点恢复后产生相同结果，不重复落地。
4. 工具配对、source 引用与 DSH 请求重建仍合法；失败后不能提交仅存在于内存的变更。
5. 不需要变更的请求前缀保持一致；允许重建时记录原因，并观察真实成本而非假定节省。
6. Windows 与实际目标运行时的适配单独验证，包含插件卸载/禁用后冷读的明确语义。

停止条件：必须绕过请求冻结才能工作；原始归属无法持久定位；不能说明跨存储部分提交怎样恢复；或会破坏用户现有会话/数据库。出现时回到设计，不以隐式降级宣称通过。

### 阶段0的建议验收边界

[ASSUMPTION: 首轮以本机 Windows、已安装 DSH 0.2.2-rc.1 的隔离会话/profile 为目标，固定提交源码只作契约参考；只验证文本/JSON工具内容，不向日常会话安装。] 真实提供商测试、凭据与 API 开销不在本次研究授权内，后续须单独确认。

受控 fixture 的通过条件可以精确判定：对应原始文本与规范 JSON 一致；减少后的正文体积小于原始体积；配对/引用错误为零；同一缩减操作重复应用不重复提交；重启前后已决定的模型可见结果一致；非重建请求的既有前缀一致。真实缓存命中率、前台延迟和大型恢复性能先记录基线，不在无实测时发明承诺值。

验证产物可以保留可复用的测试与适配证据，不默认必须丢弃，也不将未经验证的试验包装成正式插件。持久化与部分提交的恢复属于阶段0正确性；最终数据库位置和跨 harness 共享协议不必同时定案。

### 插件禁用的用户可见行为：待决定

至少必须保持 Session 可加载、原始日志可读取或导出，不得因必要消息投影解释器缺失而让冷会话无法打开。

两种仍待用户选择的目标：A）禁用后保留已缩减的可见历史，原文仍可通过日志/导出读取；重新启用再使用 ctx_expand。B）禁用时自动恢复模型可见原文，需额外恢复/迁移步骤，并会使上下文重新变大。当前不假定用户已接受其中任一项。

## 尚待用户决定

1. 已确认先编写阶段0独立验证计划；完整V1功能仍未冻结，计划审核和实施授权待完成。
2. 阶段0已确认仅文本/JSON工具内容，排除二进制附件恢复；正式产品范围仍待确认。
3. 跨 harness 是未来可扩展，还是首版必须直接共享现有 OpenCode/Pi 数据？
4. 按项目存储最重要的目标是隔离、可迁移、人工编辑还是 Git 同步？
5. 已明确面向开源发布并采用MIT；正式支持哪些DSH/模型组合仍待确认。
6. 插件禁用后仅要求原始日志可读，还是必须自动恢复模型可见原文？这是独立检查发现的用户可见取舍。
